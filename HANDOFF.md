# Castle_defence — хэндовер для другого агента/сессии

Снимок состояния на 2026-08-15. Написано, чтобы новый агент мог продолжить работу без переоткрытия всего разговора заново.

## Что это за проект

Кооп-плагин для Minecraft (Paper/Pufferfish 1.21.10) на Java 21, Maven-сборка. Игра вдохновлена Thronefall — защита замка волнами мобов, день/ночь цикл. Полный игровой дизайн — в Miro-доске "Castle Defense" (`https://miro.com/app/board/uXjVHyzi2Ws=/`), синхронизированная копия ключевых решений — в памяти проекта (`design_castle_defense_miro.md` в файловой памяти Claude Code, читается автоматически в начале любой сессии в этой директории).

**Сейчас в разработке:** система подсчёта прочности/устойчивости построек (стены и башни). Это единственная механика, реализованная в коде на данный момент — остальной геймдизайн (классы, крафты, карта) существует только на доске, кода под них нет.

## Структура кода

```
src/main/java/me/dkprog/castle_defence/
├── Castle_defence.java              — главный класс, onEnable() создаёт тестовый слот и всё связывает
└── building/
    ├── BuildSlot.java                — слот постройки: границы (BoundingBox), тип (WALL/TOWER), ось среза
    ├── BuildStats.java               — результат скана: N, сумма весов, HP (сейчас HP = доля оставшегося веса)
    ├── MaterialWeights.java          — таблица весов материалов + список декоративных блоков
    ├── BuildScanner.java             — сканирует слот, считает N/вес, умеет визуализировать число соседей
    ├── BuildListener.java            — слушает BlockPlaceEvent/BlockBreakEvent, шлёт N в чат (тестовый код)
    └── NeighborsVisualizeCommand.java — команда /visualizeneighbors, дёргает BuildScanner.visualizeNeighborCount
```

**Тестовая площадка:** куб 10×10×10 у спавна, `SlotType.WALL`, `Axis.Y` (ось среза сейчас нигде фактически не используется — раньше нужна была для слоистой плотности, которую убрали целиком, см. ниже).

## Важные архитектурные решения (кратко — полное обоснование в памяти/на доске)

- **Плотность (слоистая, по оси среза) убрана из проекта целиком** — не используется ни для HP башни, ни для боевой устойчивости стены, ни для чертежа. Осталась только в `BuildSlot.Axis`/`sliceAxis` как мёртвый неиспользуемый параметр.
- **У стены HP не используется вообще.** Устойчивость к взрывам должна определяться локальным правилом на уровне отдельного блока (см. "Что не реализовано" ниже) — этого кода ещё нет.
- **У башни HP = объёмность^k × N × вес.** "Объёмность" = среднее число заполненных соседей (0-6) по всем блокам, нормализовано /6. Логика подсчёта соседей уже есть в `BuildScanner.countFilledNeighbors` (сейчас `private`, вызывается только из `visualizeNeighborCount`) — формулу HP для башни ещё не подключали к `BuildStats`.
- **Соседи считаются как `isSolid() && isOccluding() && !isDecorative(...)`** — то есть учитываются только полные непрозрачные конструкционные блоки; заборы/стены-декор/ступени/плиты/земля-под-полом обрабатывались отдельными итерациями багфиксов (все уже внесены в `BuildScanner`/`MaterialWeights`).
- **Ступени (`STAIRS`) — структурный материал, не декор.** Планировалось (но НЕ реализовано в коде) для башенной объёмности: ступени должны засчитываться как "твёрдые" для соседей ДРУГИХ блоков (включая клетку прямо над собой), но не участвовать в своём же усреднении — иначе получается парадокс "лестницу выгоднее не строить".

## Что НЕ реализовано (следующие шаги, обсуждались подробно, но кода нет)

### Система разрушения стены (текущий фокус)
Нужны новые классы:
- `BlockPosition` — ключ для карты урона (World+x+y+z), с `equals()`/`hashCode()` (нельзя использовать `Location` напрямую из-за pitch/yaw).
- `WallDamageTracker` — `Map<BlockPosition, Integer>` накопленного урона, методы `getDamage`/`addDamage`/`clear`.
- `WallDamageListener implements Listener` — обработчик `EntityExplodeEvent`, накопительный урон (не мгновенный слом), считает соседей через (сделанный публичным) `BuildScanner.countFilledNeighbors`.

**Важный технический нюанс, который надо не забыть при реализации:** `event.blockList()` — это НЕ все блоки в радиусе взрыва, а уже отфильтрованный ванильным алгоритмом список (по raycast + ванильному сопротивлению материала). Прочный по ванильным меркам блок может не попасть туда вообще, даже если по нашим правилам (мало соседей) должен ломаться. Решение, на котором остановились: перебирать блоки в радиусе взрыва самостоятельно (`event.getLocation()` + свой радиус, НЕ завязанный на `event.getYield()`), сначала сузив границы цикла до пересечения области взрыва со слотом, и внутри цикла дополнительно проверять реальную дистанцию до центра (сфера, не куб). **Открытый вопрос, не решён:** как в итоге применять саму поломку блока — через `event.blockList()` или напрямую `block.setType(AIR)`, раз blockList() перестал быть источником истины.

**Ещё один найденный (и тоже не решённый в коде) баг:** если считать урон и сразу ломать блоки в одном проходе по списку — результат зависит от порядка обработки (сломанный ранее блок перестаёт быть "соседом" для следующего). Решение: два прохода — сначала посчитать урон для ВСЕХ блоков по снимку состояния мира до взрыва (в промежуточную `Map`), потом вторым проходом применить.

Также обсуждали, но не решили окончательно:
- Формула урона за удар и порог поломки — фиксированные или зависят от материала.
- Визуальные трещины через `Player#sendBlockDamage(Location, float)` — кому рассылать (все онлайн / только рядом), какое значение `progress` сбрасывает анимацию.
- Способность класса Инженер "чинит трещины в области, только ночью, с перезарядкой" — отдельная механика поверх трекера, дёргает `WallDamageTracker.clear(...)` для позиций в радиусе.

### Объёмность башни
`BuildScanner.countFilledNeighbors` есть, но нигде не считается среднее по всей постройке и не подключено к формуле HP в `BuildStats`. Плюс не реализована особая обработка ступеней (описана выше).

- После почти каждого изменения кода — пересобрать (`mvn clean package`) и перезапустить тестовый сервер, если просит.
